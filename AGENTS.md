# Lexicona — правила разработки

## Назначение и архитектура
Многопользовательское EN/RU web-приложение для личного словаря и обучения, доступное с телефона, планшета и компьютера. Код пишут Hermes-агенты, пользователь — заказчик. Архитектура и начальное направление UI одобрены; внешний deployment отдельно согласуется.

Стек: Python/FastAPI/Pydantic, SQLAlchemy async + aiosqlite, SQLite WAL, Alembic; React/TypeScript strict/Vite, TanStack Query, React Hook Form/Zod, CSS Modules и semantic theme tokens. Один origin, серверные cookie-сессии с CSRF. Воспроизводимая Docker Compose/Caddy поставка. Не добавлять платные API, Redis/Celery/микросервисы или менять стек без обоснования.

## Продуктовые инварианты
- Основной прогресс личного слова: integer 0–100, correct добавляет, incorrect вычитает по difficulty, с ограничением диапазона. Уровни choice+/choice−/typed+/typed−/passive+: очень легко 10/−10/20/−10/5; легко 7/−7/14/−7/3; средне 4/−4/8/−4/2; сложно 3/−3/6/−3/1; очень сложно 2/−2/4/−2/1. Не CEFR и не вероятность знания.
- SRS определяет сроки повторения отдельно от видимого процента. Snapshot/policy version/CAS/idempotency вычисляются сервером; retry одного события не начисляет прогресс повторно.
- Упражнения: карточки, выбор EN→RU и RU→EN, пары, ввод EN/RU, пропуск в примере, пассивное озвучивание в обе стороны и EN-диктант. Помощь/пропуск/TTS failure не выдавать за самостоятельный правильный ответ; самооценки отдельно от объективной accuracy.
- Подсказки RU-переводов при вводе EN: пользователь выбирает значения, ручной ввод всегда доступен, без перезаписи/дубликатов. Реальный бесплатный источник/лицензия/ранжирование проверяются до подключения; не подменять его demo fixtures.
- Первая тема тёмная, graphite/navy + gold/amber в духе Hermes; другие темы добавляются токенами, не переписыванием компонентов.

## Инженерные требования
- Перед правкой читать текущие исходники, lock-файлы и документацию. Для нового поведения/ошибки сначала воспроизводящий падающий тест, затем реализация и регрессия.
- Python: Ruff lint/format checks, mypy --strict, pytest. Frontend: strict typecheck, lint/format checks, unit/component tests и production build. Цель — 100% исполняемых строк и ветвей каждого изменённого production-файла; исключения согласуются явно. Не понижать thresholds/добавлять игнорирования ради зелёного статуса.
- Команды брать только из реально существующих project targets/config; не выдумывать готовые make/npm-команды до их создания. Проверки запускать из окружения проекта, не из runtime Hermes. Отсутствующий tool/test — not_run/blocker, не pass.
- Owner-scoping для каждого object/bulk/import/export; admin не читает личные словари. Короткие явные транзакции, отдельная AsyncSession на unit of work. Concurrent SQLite tests — file-backed WAL, не только memory.
- Приватные API no-store. Слова/ответы/auth tokens не сохранять в browser persistent storage. Очистка auth cache и защита от запоздалых ответов прежнего аккаунта обязательны.
- Безопасность, доступность/keyboard/responsive, реальные API/E2E, backup/restore и физический TTS не заменяются coverage или моками. Называть выполненными только фактически проведённые проверки.

## Организация команды и права
Только Hermes, максимум три дочерних агента одновременно, без внешних coding CLI и автономных фоновых работников. Один владелец схемы/API и непересекающиеся allowed_paths; для параллельного кода — отдельные worktree. Автор не финальный reviewer; ревью read-only, интеграцию принимает координатор. После трёх неуспешных циклов одного blocker остановить задачу и сообщить причину, не исправлять бесконечно.

Заказчик не является обязательным участником code review или приёмки каждого среза. Команда сама организует независимое ревью, исправления и повторную проверку; после ACCEPT и успешных интеграционных gates координатор переносит согласованный срез в main и выполняет push без дополнительного ручного approval. Явная пауза пользователя и отдельные ограничения системных изменений/production deployment сохраняют приоритет.

Разрешены project-local venv/npm/Docker и обычные Git операции. Системные установки, live deployment, VPN/DNS/SSH/firewall и опасные операции отдельно согласуются. Не публиковать secrets/личные данные. Перед commit/push проверять точный diff и только разрешённые пути; никогда force-add локальные артефакты.

Каждый создаваемый агентом commit завершать отдельным Git trailer после пустой строки: `Co-Authored-By: Hermes Agent (Nous Research; gpt-6.1-sol)`. Указывать фактически использованную модель, если она отличается; роль можно уточнять дополнительно. Не приписывать работу Claude или другой модели по примеру из чужого промпта. При amend/cherry-pick сохранять правдивые существующие credits и не дублировать одинаковый trailer.

## Переносимость и локальные материалы
Этот AGENTS.md предназначен для Git и должен работать после clone без обязательной зависимости от чужой домашней папки или скрытого состояния.

Проектные Hermes-skills хранятся в `.hermes/skills/<name>/SKILL.md` и предназначены для Git. Перед задачей прочитать `lexicona-workflow` (либо его SKILL.md напрямую) и product-contract из его references, затем профильную роль. На новой машине для нативного обнаружения требуется `hermes skills trust .` и новая сессия; процедура в `.hermes/README.md`. Максимум три дочерних агента. Skill не является автоматически работающим агентом, sandbox или настройкой MCP.

`.lexicona/`, `wordstudy-spec.md`, `AGENTS.override.md`, отчёты, макеты, локальные данные и credentials остаются приватными. Если локальная мастерская существует, прочитать её решения и актуальную очередь, включая `.lexicona/requirements/approved-training.md`; если её нет после clone, пользоваться этим файлом, исходниками и README. Не объявлять отсутствующие локальные файлы обязательной runtime-зависимостью и не переносить секреты в Git ради восстановления окружения.
